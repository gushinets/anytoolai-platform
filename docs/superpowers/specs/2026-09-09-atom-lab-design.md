# Atom Lab — спецификация первой версии

Дата: 2026-09-09.

Статус: согласованные в диалоге требования собраны в спецификацию. Реализация не выполнена.
Технические решения, выбранные при оформлении документа, явно отмечены ниже.

## 1. Назначение и границы

Atom Lab — закрытый внутренний инструмент для ручного тестирования и настройки существующих
11 атомов AnytoolAI. Пользователи: разработчики, QA, продукт-менеджеры и другие участники команды.
Для работы через форму не требуется знание JSON или внутреннего устройства runtime.

Основной цикл:

```text
Выбрать атом → изучить контракт → заполнить вход → изменить промпт
→ выбрать GPT-модель и reasoning → запустить → изучить результат
→ повторить эксперимент → сохранить подходящий пресет
```

Лаборатория проверяет текущее production-поведение атомов. Она использует те же контракты,
исполнитель, проверки и правила повторных попыток. Допустимые переменные эксперимента:
входные данные, промпт, модель и поддерживаемый уровень reasoning.

В первую версию входят библиотека пресетов и постоянная история запусков. Запуск составных
цепочек, их конструктор и автоматическое внедрение конфигураций в продукты не входят.

Эта спецификация заменяет для новой работы обсуждавшийся ранее редизайн stakeholder demo
с двумя режимами «Цепочки / Атомы». Документ
[stakeholder demo](2026-08-27-stakeholder-workflow-demo-design.md) описывает прежнюю страницу;
его ограничения на отсутствие истории и редактирования промпта не применяются к Atom Lab.
Удаление существующей `/demo` в объём этой спецификации не входит.

Объяснения — подготовленные описания поведения, а не дополнительный LLM-вызов.

Это схема информационной структуры, а не обещание уже работающего интерфейса. На узком экране
области располагаются последовательно. Интерфейс русскоязычный, с подписанными контролами,
клавиатурной навигацией и видимым фокусом. Статусы различаются текстом, а не только цветом.

### Вход и промпт

Форма позволяет заполнить все допустимые поля текущего входного контракта, включая вложенные
объекты, списки, enum и динамические словари. Необязательное поле можно не передавать вовсе.
Отсутствие, `null`, пустая строка, `false` и ноль не смешиваются; допустимость определяется схемой.

Форма и JSON представляют один payload. Некорректный JSON не преобразуется молча и блокирует
запуск до исправления. Проверка на сервере обязательна независимо от браузерной проверки.
Пользователь видит путь к ошибочному полю и понятное объяснение.

Промпт можно полностью изменить и восстановить до исходного. Редактируется инструкция
конфигурации; runtime продолжает добавлять вход и служебную схему по существующим правилам.
Сохранение и запуск не перезаписывают исходный промпт в репозитории.

Переключение атома, пресета или восстановление запуска не уничтожает несохранённые правки без
предупреждения. Заполнение примера не подменяет результат ранее выполненного запуска.

### Выход

Показываются читаемый результат и полный нормализованный JSON успешного ответа. Значимые поля
не скрываются за сокращённым пересказом. Ошибочный ответ не показывается как успешный артефакт.
Внутренние диагностические детали могут содержать текст невалидного ответа и ошибки проверки,
с явной пометкой «не прошёл контракт»; credentials и скрытые reasoning traces не выдаются.

Выход и схемы не редактируются. Поле ожидаемого ответа, автоматическое улучшение промпта,
LLM-судья и автоматическая оценка качества отсутствуют в первой версии.

Универсальное новое правило языка не внедряется скрыто: результат зависит от фактически
использованного промпта и полей действующего контракта. Языковые ограничения можно проверять
через эти средства. Ранее обсуждавшееся новое общее поле `output_language` не добавляется в
контракты атомов в рамках Atom Lab.

## 4. Выполнение и structured output

Сохраняется текущий путь:

```text
Внутренний API → scenario session → job → worker → ActionRunner
→ StructuredLlmActionExecutor → PydanticAI PromptedOutput
→ ProviderGateway → LiteLLM SDK → OpenAI
→ проверки и validation retries → финальная валидация → artifact
```

Каждый принятый запуск получает `scenario_session_id`, job и action run. Одиночный атом может
использовать существующий одношаговый scenario/workflow механизм. Новый параллельный executor
для лаборатории не создаётся.

- Схема передаётся в служебных инструкциях по текущему production-пути.
- Нативный `response_format: json_schema`, преобразование схем под OpenAI strict mode и
  переключатель structured-output режимов не входят в работу.
- Сохраняются typed output binding, input/output cross-validation и финальная проверка платформы.
- Validation retries принадлежат PydanticAI; transport retries — ProviderGateway.
- Каждый физический вызов учитывается в provider-call ledger; скрытые retries LiteLLM выключены.
- Модель и reasoning неизменны в пределах одного запуска и его повторных попыток.

Снимок настроек фиксируется до исполнения и доступен worker после перезапуска процесса.
Экспериментальный промпт и выбор выполнения передаются как изолированные настройки запуска:
запрещены мутация общего registry, изменение process-wide defaults и утечка в соседние jobs.

UI показывает очередь, выполнение, успех или ошибку. Повторный клик/повтор HTTP-запроса при
сетевом сбое не должен создавать второй платный запуск. Явное повторение эксперимента создаёт
новый запуск. Закрытие страницы и timeout polling не отменяют backend job; его можно открыть
из истории и продолжить наблюдение. Несохранённые изменения формы не меняют выполняющийся запуск.

## 5. Модели и reasoning

Первая версия работает только с реальным OpenAI и подходящими текстовыми моделями семейства GPT.
Другие провайдеры, произвольные base URL, ввод API-ключа в браузере и универсальная панель
provider-параметров не входят. Fake provider допустим в автоматических тестах, но не выдаётся
за реальное исполнение в рабочем интерфейсе лаборатории.

### Источники каталога

1. OpenAI Models API — доступные модели, их идентификаторы и доступные сведения об отключении.
2. Справочник возможностей LiteLLM — назначение модели, поддерживаемые параметры и известные
   сведения о reasoning. Точный перечень уровней используется только если источник его содержит.
3. Небольшой YAML со специальными поправками в слое provider configuration — подтверждённые
   сведения, которых нет в справочнике или которые требуется исправить.

Поправка имеет приоритет над внешними метаданными, но не делает недоступную модель доступной.
Для поправки указываются источник и дата проверки. Знание `supports_reasoning=true` само по себе
не означает поддержку любого уровня. Не выводить уровни из одного префикса имени модели.

Backend периодически обновляет Models API и JSON-справочник LiteLLM, валидирует ответы и хранит
последний корректный снимок. Кнопка «Обновить модели» запускает тот же процесс. При сбое
обновления прежний список не стирается: отображаются устаревание и время успешного обновления.
Если корректного снимка ещё нет, показывается ошибка загрузки и возможность повторить.
Частота обновления — именованная серверная настройка; конкретный интервал выбирается в плане
реализации и не является отдельным пользовательским требованием.

Внешние метаданные не являются исполняемыми конфигурациями: они не могут задавать credentials,
адрес провайдера или изменять лимиты. Обновление справочника не обновляет код LiteLLM;
новая несовместимая модель может потребовать обновления SDK/адаптера.

### Поведение выбора

- UI получает подготовленный каталог от backend и показывает только релевантные текстовые GPT
  модели; наличие `gpt` в имени не является достаточным критерием (есть audio/realtime/image).
- Для известных возможностей доступны только подтверждённые уровни reasoning.
- При известном отсутствии reasoning контрол неактивен с объяснением.
- При отсутствии сведений показывается «Возможности не проверены», а не «Не поддерживается».
- Техническое решение первой версии: модели с неизвестной совместимостью видны отдельно, но
  запуск заблокирован до получения достаточных метаданных/поправки. Автоматического перебора
  параметров платными пробными вызовами нет.
- Отсутствие нативного JSON Schema не исключает модель: Atom Lab использует prompted output.
- Backend проверяет выбранную модель и уровень до принятия запуска. Нельзя незаметно отбросить
  выбранный reasoning или подменить модель; несовместимость показывается как ошибка.
- Сохранённый пресет с исчезнувшей моделью доступен для чтения; новый запуск требует явной замены.

Снимок запуска содержит запрошенную модель, идентификатор модели из ответа провайдера, выбранный
reasoning и источник/версию метаданных. Не заявлять, что провайдер подтвердил фактический уровень
reasoning, если он его не возвращает. Алиас модели может измениться у провайдера: восстановление
настроек не обещает побитового воспроизведения результата.

## 6. Библиотека пресетов

Библиотека общая для внутренней команды. Пресет — именованная экспериментальная конфигурация
конкретного атома. Можно создать новый пресет, открыть существующий и сохранить новую версию.
Версии неизменяемы; сохранение следующей не меняет предыдущие и использовавшие их запуски.

Версия содержит:

- идентификатор, номер версии, название, назначение и дату сохранения;
- тип атома, исходную action configuration и ссылки/версии входного и выходного контрактов;
- редактируемый промпт и происхождение исходного промпта;
- фиксированные входные настройки и поля, передаваемые при запуске;
- пример входа для повторной проверки;
- выбранную OpenAI-модель и настройку reasoning;
- ссылку на исходный эксперимент, если сохранение сделано из запуска.

Фиксированные настройки отличаются от данных конкретной задачи. Например, в A01 список
извлекаемых полей можно сохранить как настройку, а `source_text` передавать при запуске.
Техническое решение первой версии: назначение фиксируется на уровне целого верхнеуровневого
поля контракта, включая весь вложенный объект/список; произвольных overlapping JSON-path bindings
нет. Схема не меняется. Для тестирования итоговый payload всегда проходит обычную валидацию.

Редактирование фиксированного поля создаёт несохранённое изменение пресета. Оно может быть
проверено запуском без предварительного сохранения. В полном JSON нет скрытого слияния,
которое перезаписывает введённое пользователем значение.

Одновременные сохранения не теряют чужую работу: backend проверяет базовую версию и при конфликте
предлагает открыть актуальную или сохранить отдельный пресет. Запускать можно и неудачно
настроенный промпт; пресет не получает статус «проверен» только по факту сохранения.

### Дальнейшее переиспользование

Первая версия предоставляет экспорт конкретной версии: промпт, фиксированные параметры,
пример, ссылки на контракт и настройки выполнения. Пакет имеет версию формата и не содержит secrets.
Импорт произвольных пакетов и автоматическое создание PR не требуются в первой версии.

Перенос в продукт или цепочку выполняется отдельным изменением YAML/Markdown с обычной проверкой
репозитория. Модель/параметры разрешаются в provider policy; raw provider fields не вставляются
в product action config. Нажатие «Сохранить» не публикует конфигурацию и не меняет production.

## 7. Постоянная история

История хранится на backend и доступна после закрытия страницы/перезапуска сервиса. Показывается
простой список с постраничной загрузкой, временем, атомом, пресетом/версией при наличии, моделью
и статусом. «Небольшая» означает простой интерфейс, а не автоматическое удаление старых записей.

При открытии доступны:

- точный исходный payload и промпт, выбранные модель/reasoning;
- ссылки/версии контрактов и сохранённый контекст исполнения, достаточный для объяснения запуска;
- нормализованный результат либо безопасная диагностика ошибки;
- длительность, validation attempts, transport attempts и физические вызовы как разные величины;
- факт успеха с первой попытки либо после исправлений;
- идентификаторы session/job/action/artifact для внутренней диагностики.

Конфигурационный снимок неизменяем с момента принятия; статус и результат дополняются по мере
исполнения и становятся неизменяемыми после завершения. История отражает сбои и незавершённые
запуски, а не только успехи. Ошибки до принятия запуска показываются в форме.

«Повторить с этими настройками» восстанавливает форму и не запускает платный вызов автоматически.
Из истории можно сохранить пресет. Если контракт больше недоступен, запись остаётся читаемой,
но нельзя молча исполнить её по новому контракту: необходима явная адаптация к текущей версии.

В первой версии история, как и библиотека, общая для команды. Отдельные аккаунты, личные списки
и права на уровне записи не согласовывались и не добавляются. Сравнение запусков бок о бок,
массовые прогоны и автоматические оценки отложены.

## 8. Хранение и архитектурная граница

Техническое решение для планирования: лабораторные пресеты, версии и снимки запусков хранятся
в PostgreSQL как внутренние экспериментальные данные, с привязкой к существующим runtime IDs.
Action runs, provider calls, artifacts и события остаются в существующем runtime; отдельный ledger
или второй механизм выполнения не создаётся. Конкретная структура таблиц определяется планом
реализации после проверки существующего storage.

Это целевое ограниченное расширение текущих правил проекта, а не уже существующая возможность:

- [Core beliefs](../../core-beliefs.md) запрещают обычным frontend выбирать промпт и модель.
  Atom Lab получает исключение только на защищённых внутренних маршрутах.
- [Scope source of truth](../../product-specs/mvp-scope-source-of-truth.md) запрещает DB-реестр
  рабочих action/prompt definitions в MVP-A. Экспериментальная библиотека не заменяет этот реестр;
  её отдельное хранение должно быть явно отражено как внутреннее расширение при реализации.
- [Client Surfaces](../../product-specs/mvp-a2-client-surfaces.md) и публичные Result API не
  получают доступ к лабораторным промптам, снимкам и диагностике.

Atom Lab не становится новым Freelancer-продуктом или условием завершения существующего MVP-A1.
До внедрения соответствующих runtime/storage расширений реализация должна синхронно обновить
controlling scope, архитектурные документы и guards узким исключением для лаборатории.
Этот документ не отменяет существующие ограничения для остальных клиентов.

`apps/platform-api` остаётся composition root. UI и библиотека не импортируют provider SDK.
Динамическое получение моделей и provider-specific capability logic находятся в provider boundary.
PydanticAI остаётся в structured executor. Продуктовые пакеты не импортируются в Core/Actions.

## 9. Внутренний доступ и надёжность

Все операции каталога, промптов, пресетов, истории и запуска требуют внутреннего доступа,
проверенного сервером. Общая библиотека означает доступ команды, а не публичный доступ по URL.
Техническое решение v1: отдельный серверный access code для Atom Lab в закрытом развёртывании;
не использовать секрет публичной демки как неявное разрешение к лаборатории. При отсутствии
настройки доступ закрыт. Для доступа через сеть требуется HTTPS.

Нет регистрации, ролей и SSO в первой версии. Secrets не хранятся в пресетах/истории и не
передаются браузеру. Модельный текст отображается безопасно, без выполнения HTML/скриптов.

Размер payload/промпта, число принятых запусков и concurrency ограничиваются backend-настройками.
Окончательные численные значения задаются в плане реализации; прежний лимит stakeholder demo
50/сутки не считается автоматически утверждённым для Atom Lab. Retry hard caps сохраняются.

Нельзя записывать input/prompt/response в обычные HTTP-логи; эти данные доступны только через
защищённую историю. Операции записи пресетов атомарны; отказ сохранения оставляет рабочий draft.

## 10. Критерии приёмки

1. Все 11 атомов доступны с актуальными описаниями, контрактами и исходными live-промптами.
2. Форма позволяет выразить все допустимые входные поля, в том числе вложенные/необязательные,
   и различает отсутствие, пустое значение, ноль, `false` и допустимый `null`.
3. Промпт редактируется и восстанавливается; входной/выходной контракт редактировать нельзя.
4. Изменённый промпт и выбранная модель/reasoning применяются только к нужному запуску,
   включая worker execution и retries; соседние и обычные production jobs не меняются.
5. Выполнение использует существующий prompted-output путь, реальные calls и финальную проверку.
   Нативная schema support не является фильтром допуска модели.
6. Каталог моделей обновляется; неизвестные capabilities, unsupported reasoning, недоступная
   модель и сбой обновления отображаются различимо. Неподдерживаемый выбор не игнорируется.
7. Новый пресет и новая версия сохраняются, повторно открываются после закрытия страницы;
   предыдущие версии не изменяются. Конкурентное сохранение не теряет данные.
8. История содержит принятые успешные и неуспешные запуски, точные снимки и счётчики попыток.
   Повторение из истории заполняет форму без автоматического вызова модели.
9. После закрытия вкладки можно снова открыть текущий/завершённый запуск. Повтор HTTP-запроса
   не создаёт дублирующего запуска. Ошибка не скрывается как успех или пустой результат.
10. Экспорт версии не содержит secrets и позволяет разработчику перенести настройки в
    repo-owned конфигурацию без изменения контракта атома.
11. Неавторизованный доступ к каталогу, пресетам, истории, промптам и запуску отклоняется.
    Обычные публичные API не выдают лабораторные данные.
12. Доступны клавиатурная навигация, понятные ошибки, читаемый результат и JSON; несохранённые
    правки не теряются при навигации без предупреждения.

Проверки реализации: целевые API/storage/runtime tests, проверки изоляции и отрицательные
тесты границ, browser-проверки ключевых пользовательских путей, live evidence для всех 11 атомов
на одной доступной GPT-модели и проверки передачи выбранного reasoning на поддерживаемых
комбинациях. Fake fixtures не являются доказательством live-совместимости. Выполняются
канонические repository checks, включая PostgreSQL-проверки для новых durable/concurrent путей.

## 11. Явно отложено

- Цепочки, визуальный workflow builder, выполнение сохранённого пресета в продукте без review.
- Другие провайдеры, собственные API endpoints, универсальный редактор параметров модели.
- Переход на native JSON Schema, изменение контрактов атомов, автоматический fallback режимов.
- Автоматическая оптимизация промпта, ожидаемые ответы, graders, batch evaluations.
- Side-by-side сравнение, личные кабинеты, роли, публикация/маркетплейс пресетов.
- Автоматическое удаление истории и автоматические платные capability probes.

## 12. Основания и актуальность сведений

Продуктовые решения: обсуждение с владельцем продукта, завершённое 2026-09-09.
Подтверждённый текущий код: `structured_llm/pydanticai_runner.py` использует `PromptedOutput`,
а provider adapter `providers/adapters/litellm.py` добавляет schema guidance к сообщениям.
Это наблюдение текущей реализации, а не гарантия неизменности файлов после написания документа.

- [OpenAI Models API](https://developers.openai.com/api/reference/resources/models/methods/list):
  список моделей не является полным capability API.
- [LiteLLM structured-output support](https://docs.litellm.ai/docs/completion/json_mode):
  метаданные библиотеки описывают поддержку функций, но не доказывают конкретный runtime run.
- [PydanticAI output modes](https://pydantic.dev/docs/ai/core-concepts/output/): prompted output
  является отдельным способом выполнения с валидацией.
- [LLM runtime](../../architecture/llm-runtime.md): ownership retry, gateway и финальной проверки.

Будущие изменения API/метаданных должны проверяться при реализации и обновлении каталога;
спецификация намеренно не фиксирует быстро устаревающий список GPT-моделей и уровней.
